Waterflood Injection Evaluation & Optimization — Architecture

One document for the whole application: what the user experiences, what the engine does behind it, and how the result becomes a trusted field action. Consolidates the CRM methodology review, the five-layer blueprint, the data-loader design, the model-tournament selector, the sampling/pressure rules, and the gap analysis.

1Purpose & design principles

Turn routine production/injection data into a monthly, auditable injection plan using capacitance-resistance models, without asking the user to understand the models.

  • Encapsulation — the user path is load → confirm mapping → pick wells → run. Every technical choice (method, τ, Δt, solver) is automatic and hidden behind a "Details" panel.
  • Physics first, ML as correction — every deployed model exposes fij, τ, J. Pure black-box forecasters are benchmarks only.
  • Evidence before recommendation — nothing is shown without a blind test and a confidence level.
  • Reproducible — data snapshot hash + config + code version stored per run.
  • Actionable — output is a ramped, approved change list, not a parameter table.
  • Self-correcting — implemented changes are evaluated against forecast, and that evaluation re-scores the model.

3Roles & approval workflow

A recommendation has a lifecycle. "Evaluated" is what closes the surveillance loop and feeds the validation record (§16).

RuleDetail
SeparationThe person who runs cannot approve. Advanced-mode overrides require reviewer role and are shown in the approval view.

4Five-layer engine architecture

5Data loading (L1)

Sources & mapping

  • SQL (Oracle/OFM, SQL Server, PostgreSQL, MySQL, SQLite) via a backend connector with read-only credentials; optional view/query override. The browser never opens a database socket.
  • CSV one file per dataset; Excel one workbook, sheets become candidate tables.
  • Four canonical datasets: rates (required), pressure, coords, category. Column mapping auto-suggested from naming conventions; required fields flagged; missing optional tables degrade features rather than block.
  • Category table drives a cascading field → reservoir → block filter.
  • Mapping, filter and well list are saved as the project config; monthly refresh re-runs identically.

Well type derived from rates, not from a master table

  • Per time step: production > 0 → P, injection > 0 → I, both → B (flagged as a data-quality issue).
  • Well type = PROD or INJ if a single mode ever appears, else MIXED with conversion dates.
  • MIXED wells are split into separate injector-role and producer-role series per period, so the CRM sees a converted well as two entities with a date boundary. A conversion is also written to the events table.
  • Multi-select with search and one-click groups (producers / injectors / mixed / active last 12 months).
Commingled / multi-reservoir wells: rates are split by the allocation factor from the category table (or equal split with a warning). The split factor is stored per well and can be overridden in advanced mode.

6Units, conventions & reservoir-volume conversion

TopicRule
Unit systemProject-level setting (field / metric / mixed). Every column carries a unit tag from mapping; a units service converts once at load and stores SI internally. Display converts back.
Reservoir volumesCRM balances reservoir barrels: qres = qoBo + qwBw + (qg − qoRs)Bg; injection ires = iwBw. Bo, Rs, Bg taken from PVT table at average reservoir pressure (static surveys or CRMPA estimate); constant values allowed with a warning.
Free gasIf producing GOR exceeds Rs (below bubble point), the free-gas term is included in the total-fluid balance and the run is flagged "gas-affected — reduced confidence". Gas injection / WAG is out of scope for this release (§20).
Time baseRates normalised by days_on to calendar-day rates; volumes preserved. Shut-in months keep days_on = 0 rather than rate = 0.
DatumAll pressures shifted to a project datum with a fluid gradient; pressure source and datum stored with each value.
NamingWell IDs normalised (case, whitespace, aliases table) so the four datasets join reliably; unmatched IDs are reported, never silently dropped.

Data-quality report (shown as a traffic light, detail in "Details")

  • Coverage per well, gap count, outliers removed, simultaneous P+I steps, unmatched IDs
  • Identifiability summary per sector
  • Units and PVT assumptions used
  • Report stored with the run; a change in the report between refreshes is itself an alert (§15)

8Sampling frequency & pressure data

Δt versus τ

  • Default grid monthly; minimum 36 steps, ideally 60–120. Finer Δt never substitutes for history length.
  • Rule Δt ≤ τ/5 preferred, τ/3 minimum; τ estimated from a quick CRMT or ctVp/J. If τF < 3Δt and metered daily data exist, resample finer; if production is monthly-allocated, a finer grid adds noise, not information — stay monthly and prefer CRMT/CRMP.
  • Injection and production always on the same grid, aligned by days-on.
  • Daily/weekly grids justified for close-spaced high-permeability patterns, injector-interference or crossflow variants, and the ML residual layer.

Pressure handling by source

Downhole gaugeUse flowing pressure; average to rate grid; buildups calibrate J independently.
ESP intake (PIP)Remove trips/gas-lock; shift PIP to mid-perf with a water-cut-dependent mixture gradient; average to grid; keep Hz/choke changes as events — they are the pwf steps the J·dpwf/dt term explains. Trip build-ups used as mini-PBUs to bound J.
WHP onlyCalculated BHP accepted with a bias check; constant-BHP mode preferred unless WHP varies strongly.
Static surveysNot pwf(t); used to validate CRMPA pore volume and bound τ.
NoneConstant-BHP formulation; crossflow variant ineligible; lift changes must be in the events table.

9Model engine & tournament (L3)

ItemDesign
Calibrated model objectfij, τ, J, q₀, oil-cut / Koval parameters, aquifer terms, fit metrics, UQ ensemble, window definition, data hash, code version. Stored in the run registry.
Fit orderCRMT per sector (seconds, sanity) → CRMP → CRMIP only where CRMP residuals show pair structure → oil-cut → optional ML residual if residuals remain autocorrelated.
Confidence badgeHIGH: blind R² ≥ 0.85 and parameter spread < 15 % and no gate warnings. MEDIUM: R² ≥ 0.7 or one warning. LOW: otherwise — recommendation shown as "screening only", cannot be approved without reviewer override. Thresholds calibrated by §16.
pywaterfloodUsed as the Phase-1 CRMP/CRMIP/MPI engine and later as a regression baseline for the in-house solver.

10Time-varying connectivity & change detection

Rolling-window fitting

  • Besides the full-history fit, the engine fits overlapping windows (default 36 months, step 6) and stores fij(t), τ(t) per window.
  • Event boundaries (infill, workover, conversion) force a window break.
  • The forecast and the optimizer use the latest window's parameters, weighted with the full-history fit by their blind-test scores.

Change alerts

  • Per pair: CUSUM on fij(t) and τ(t) relative to the multi-start spread; a shift larger than 2× spread that persists for two windows raises "connectivity between I-3 and P-7 has shifted since March".
  • Per producer: forecast-error monitoring (§15) distinguishes reservoir change from data problems.
  • Alerts appear in plain language with the likely cause list (breakthrough, new well, fault, meter) and a link to the Details plot.

12Optimization & economics (L4)

ElementDesign
Decision variablesInjection rate per injector per period over a 6–24 month horizon; optionally producer BHP / choke targets.
Objectives (user picks)Max cumulative oil · Max NPV = Σ(oil price·qo − water-handling cost·qw − injection cost·i)/(1+r)t · Min water for target oil.
ConstraintsTotal water available; per-injector min/max (injectivity, frac gradient); producer liquid / ESP limits; max water cut; VRR band per pattern; reservoir-pressure window (above bubble point, below parting pressure).
AlgorithmSLSQP / trust-region for smooth short horizons; ensemble (EnOpt) or GA for long horizons and robust objectives.
Economics inputsPrice deck, cost per bbl water handled, cost per bbl injected, discount rate — project-level with scenario overrides; sensitivity to price shown as a tornado.

Scenario manager

  • Base (hold current) · Reallocation (same water) · Water-budget sweep (marginal value of water) · Shut-in / convert / new well (§11) · Pattern balancing (VRR targets)
  • Every scenario stores inputs, model version, objective, posture, results and delta-vs-base.
  • Scenarios are compared on the same UQ ensemble so differences are not noise.

13Uncertainty → decision

P10/P50/P90 fans describe uncertainty; the risk posture decides what to do with it. The posture is a user setting on the Run screen, with "balanced" as default.

PostureObjective actually optimizedTypical user
AggressiveP50 (expected value) of the objective across the calibrated ensemblemature asset, reversible changes
BalancedExpected value minus 0.5 × standard deviation (mean-variance)default
RobustMaximize the P10 outcome (worst-case among realizations); also rejects plans that lose oil in any realizationconstrained facilities, low confidence
The confidence badge and the posture interact: a LOW-confidence model forces the Robust posture and reduces the allowed step size (§14).

14Operational recommendation — "what to change this week"

RuleDefault
Ramp rate≤ 15 % of current rate per week per injector (HIGH confidence), ≤ 8 % (MEDIUM/LOW); configurable per facility.
Minimum actionable changeChanges below 5 % or below meter resolution are suppressed to avoid churn.
Setting translationTarget rate → choke / pump-frequency suggestion using the last known injectivity curve; the field confirms the actual setting.
OrderingHighest marginal-oil changes first; changes touching the same facility grouped.
ReversibilityEach change carries a "revert if" condition (water-cut jump, pressure limit) monitored by §15.

Output artefacts

  • Change list (well, from → to, step this week, target date, setting hint, expected oil gain, revert condition)
  • Forecast fan per producer and field with the implemented-plan overlay
  • Connectivity and τ maps, injector efficiency (oil per bbl injected)
  • Report (PDF/DOCX), tables (XLSX/CSV), model JSON, optional writeback of targets to the surveillance system

15Surveillance loop — rules

TriggerAction
New month of dataRe-run L1–L2 with saved config; data-quality report diffed against last run. Forecast error for the past month computed per producer.
Forecast error within P10–P90No re-fit; parameters kept; plan continues.
Forecast error outside band, data-quality unchangedReservoir-change hypothesis → rolling re-fit (§10) → if parameters shift, re-optimize and open a new DRAFT; the running plan's "revert if" conditions are checked.
Forecast error outside band, data-quality changedData-problem hypothesis → user message names the well/meter; no re-fit until resolved.
New event (workover, conversion, new well)Window break; affected sector re-fit; prior-based parameters for new wells (§11).
QuarterlyFull tournament re-run (method choice may change as history grows); confidence recalibrated from §16 outcomes.
Implemented plan reaches 3 / 6 monthsEvaluation record created (§3); outcome class feeds validation.

16Validation strategy

Tier 1 — synthetic ground truth

  • Reservoir-simulator cases with known fij, τ: 5×4 streak field; aquifer-supported; converted wells; monthly-allocated noisy rates; large 60-well sectored field.
  • Every solver change runs the suite in CI; pass = parameters within tolerance and blind R² above floor.
  • pywaterflood results as an independent baseline.

Tier 2 — historical field back-tests

  • At least one asset with a documented reallocation: fit on data before the change, forecast the change, compare with what actually happened.
  • Establishes the mapping from blind-test metrics to realised-outcome accuracy — i.e. what HIGH / MEDIUM / LOW actually mean.

Tier 3 — live calibration

  • Every EVALUATED recommendation (§3) adds a point: predicted band vs. realised.
  • Confidence thresholds are re-tuned quarterly so that a HIGH badge means ≥ 80 % of past HIGH recommendations landed within band.
  • A validation dashboard is part of the admin view.

18Governance, security & deployment

TopicDesign
Database accessBackend service holds read-only credentials in a secrets store; browser calls the API only. Query override is restricted to reviewer/admin and logged.
Data residencyOn-prem or private-cloud deployment; no field data leaves the corporate network. Container images signed and pinned.
Access controlRow-level: users see only assets they are assigned; roles per §3.
AuditEvery load, run, override, approval and implementation entry is logged with user, time, data hash and config hash. Logs are PII-free (user ID only).
