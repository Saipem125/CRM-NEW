# DECISIONS.md — choices made where the spec was silent or conflicted

Each entry: date · milestone · section · decision · why. Newest at the bottom.

## Milestone 0

- **2026-09-03 · M0 · §19 — Repository layout.** Git root is `waterflood-optimizer/`; the importable Python package is `waterflood_app/` laid out exactly as the §19 tree (`ingest`, `prep`, `models`, `optimize`, `outputs`, `workflow`, `validation`, `messaging`, `store`, `api`, `ui`). Paths quoted without a prefix in the build prompt (`validation/synthetic_suite/`, `messaging/condition_map.yaml`, `ui/src/…`, `outputs/templates/`) live under `waterflood_app/`; `docs/`, `tests/`, `config/`, `pyproject.toml`, `CHANGELOG.md` sit at the git root. *Why:* keeps the §19 tree intact while still giving one installable package and one place for tests and config.
- **2026-09-03 · M0 · §2 of prompt — Python version.** The build machine has Python 3.11.9 and no 3.12. Code targets `>=3.11`; CI matrix runs 3.11 and 3.12. Nothing 3.12-only is used. *Why:* unblock the build now; 3.12 remains the deployment target.
- **2026-09-03 · M0 · §16 Tier 1 — Fixture generator physics.** Fixtures are generated by a CRM-forward simulator (Sayarpour et al. 2009 discrete CRMP solution, Atlas "CRMP" tab), not by a finite-difference simulator. *Why:* the acceptance criteria are stated as parameter recovery (f_ij within 10 %, τ within 20 %), which is only well-posed when the truth *is* a CRM parameter set. A 2-D single-phase FD case would need its own procedure to define "true" f_ij (tracer or perturbation runs) and is recorded as a follow-up under `validation/synthetic_suite/README.md` → "Future work". Aquifer, conversions, allocation noise and sectors are layered onto the same forward model as documented in the README.
- **2026-09-03 · M0 · §9 / Atlas CRMP tab — Direction of the Σf_ij constraint.** The Atlas CRMP equation prints `Σ_i f_ij ≤ 1` (sum over injectors for a producer). The mass-conservation constraint used by Sayarpour 2009 and by pywaterflood is `Σ_j f_ij ≤ 1` for each injector (an injector cannot allocate more than 100 % of its water). §9 separately uses the per-producer sum `Σ_i f_ij > 1.15` as the aquifer signature. Fixtures and the engine apply the per-injector constraint and report the per-producer sum as the aquifer diagnostic. *Why:* the two are different quantities; the per-injector one is the physical constraint, the per-producer one is the diagnostic §9 asks for.
- **2026-09-03 · M0 · §16 — Definition of "within 10 %" for f_ij.** Pairs with true f_ij ≥ 0.05: relative error ≤ 10 %. Pairs below 0.05 (barriers / negligible): absolute error ≤ 0.02. τ: relative error ≤ 20 % per producer. *Why:* relative error on near-zero pairs is meaningless; barriers must still be recovered as barriers.
- **2026-09-03 · M0 · §6 — Fixture data schema.** Long format, one row per well per month: `well_id, date, days_on, q_oil, q_water, q_inj, bhp`. Rates are calendar-day rates in bbl/d (monthly volume ÷ days in month); `days_on` is the producing/injecting days; `bhp` is null unless the case includes pressure. Companion tables `coords` (`well_id, x, y`), `category` (`well_id, field, reservoir, block, alloc_factor`), `events`. *Why:* matches the canonical four datasets of §5 and the days-on rule of §6 without inventing extra columns.
- **2026-09-03 · M0 · prompt §3 — Node.js absent on the build machine.** Milestone 4 (React/Vite UI) will need Node 20+; it is not installed. Flagged now so it can be provisioned before Milestone 3 closes.
- **2026-09-03 · M0 · §9 — Correction: what the "Σf_ij > 1.15 aquifer signature" measures.** The earlier entry said the per-producer sum is the aquifer diagnostic. That is wrong: a producer fed by several injectors legitimately has Σ_i f_ij > 1 (in `streak_5x4`, P-3 receives 1.59 with no aquifer). The physical signature of unmodelled support is an *injector* allocating more than 100 % of its water when the fit is unconstrained, equivalently field production exceeding field injection: `apparent_support_ratio = ΣQ/ΣI` in `truth.json` (1.43 for `aquifer_6x9`, ≤ 1 elsewhere). The §9 gate is implemented on that quantity in Milestone 1; the constrained engine keeps Σ_j f_ij ≤ 1 per injector.
- **2026-09-03 · M0 · §8 / Atlas CRMP — Discrete time convention.** Δt_n = t_n − t_{n−1} is the length of the interval that *ends* at grid point n; i(n) is the injection over that interval; q(n) is the rate at t_n. The injection of the interval ending at t_0 is already inside q(0) and contributes nothing later. `month_grid`, `to_matrices` and the forward model all use this convention; the in-house solver (M1) must too.
- **2026-09-03 · M0 · §9 — pywaterflood baseline alignment.** pywaterflood 0.3.4 adds a `(1−e^{−Δt/τ})·f·i(0)` response at the first sample on top of its primary term `gain_p·q(0)·e^{−t/τ_p}`, so its q̂(0) can never equal q(0) with gain_p = 1. Zeroing i(0) in the arrays passed to pywaterflood makes its convolution identical to the Sayarpour recursion above; the acceptance test does this (`tests/test_fixtures.py::_pwf_inputs`). With the alignment the noise-free recovery is exact (errors < 1e-4); without it the worst pair error was 10.4 %.
- **2026-09-03 · M0 · §7 — O_d for sectored fields.** `sectored_60` has O_d = 120/(24+1) = 4.8 for the whole field (fails the gate) and 9.2 per sector (passes). `truth.json` reports `O_d` on the basis the engine is expected to use (per sector, `O_d_basis`) and `O_d_field` for reference. Sectorization (§7) is therefore a hard requirement for this case, not an optimisation.
- **2026-09-03 · M0 · §16 — Aquifer case tuning.** Fetkovich tank parameters (J_aq = 14 bbl/d/psi, p_aq0 = 3400 psi, p_r0 = 3000 psi, c_t·V_r = 4·10⁴ bbl/psi, c_t·V_aq = 2.5·10⁵ bbl/psi) were chosen so the support ratio lands at 1.43 (prompt: "≈ 1.4"); influx declines from 5600 to 3290 bbl/d over 160 months (partial, declining-pressure drive as the Atlas requires for CRMPA).
- **2026-09-03 · M0 · prompt §2 — ruff configuration.** `RUF001/002/003` (ambiguous unicode) are disabled: Greek letters, × and → are the notation the docstrings must use to cite the Atlas equations. Everything else in `E, F, W, I, N, UP, B, ANN, RUF` is enforced; `mypy --strict` is clean.
- **2026-09-03 · M0 · §16 — Noisy-variant baseline.** On `streak_5x4_noise5` pywaterflood's single-start fit reaches R² = 0.895 (noise ceiling ≈ 0.89) with τ within 13 % but one small pair (true f = 0.075) off by 42 %. The M0 test only asserts R² ≥ 0.8; pair-level tolerance on noisy data is a Milestone 1 target for the multi-start in-house solver.

## Milestone 1 — engine core (2026-09-03)

- **M1 · §9 / Atlas CRMP — Primary-depletion term is tied to τ by default.** The Atlas capacitance model writes the initial-state decay as q(t₀)e^{−(t−t₀)/τ}. pywaterflood frees it (gain_p, τ_p). The free form lets a slowly declining external influx (an aquifer) hide in a long τ_p primary term instead of inflating Σf, which silently defeats the §9 "Σf_ij > 1.15 → aquifer" gate (observed on the external `aquifer_9x9` case: flank sums 0.92/0.74 with the free form, 1.34/1.25 with the tied form). Default `solver.free_primary: false`; the free form remains available and is what the in-house-vs-pywaterflood 1 % regression test uses, so like is compared with like.
- **M1 · §9 — Solver strategy: variable projection before gradient descent.** Multi-start L-BFGS-B alone converged to local minima on the external streak case (SSE 1700 vs. 7 at the truth; f_ij errors up to 72 %). For fixed (τ, τ_p) the CRMP model is linear in (f, g_p, J), so the solver now searches τ on a log grid + Nelder–Mead with bounded least squares inside (VarPro), then polishes with the analytic-gradient L-BFGS-B from that solution and from random starts (the ensemble). After this the external streak recovers f_ij within 5 % and τ within 1 %. CRMIP is seeded from the CRMP VarPro solution.
- **M1 · §7 — Injection is never smoothed.** Hampel/MAD is applied to producer liquid only; injection is a control input (a spike is real water) and is only capped at zero. Applied to injection it replaced short shut-ins and re-targets in the external fixtures and corrupted the model input. For producers the filter replaces only *isolated* spikes (deviating from both neighbours) with k = 5 MAD and ≥ 25 % deviation; zero/shut-in steps never enter the statistics (§7 "short shut-ins retained as signal").
- **M1 · §9 — What "Σf_ij > 1.15" measures (supersedes the M0 wording).** Three quantities are computed from a quick two-start CRMP with tied primary, no per-injector coupling and a distance mask (`solver.quick_fit_distance_factor` × median nearest I–P distance): (a) the field support ratio ΣQ/ΣI; (b) the unconstrained per-injector Σ_j f_ij; (c) the per-producer apparent Σ_i f_ij. The influx gate is (a) > 1.15 **or** max(b) > 1.15 — an injector "delivering" more than it injects is the physical signature. (c) is informational: producers above 1.15 and 1.3× the median of the others are named as flank wells in the message. A streak (M0 `streak_5x4`, P-3 receives 1.59) does not trigger the gate because every injector row stays ≤ 1; both aquifer cases do (M0: ratio 1.43; external: injector rows 1.78/1.79 with ratio 0.76 — that field has a net injection deficit *and* an aquifer).
- **M1 · §16 — External fixture set vendored.** `New CRM/synthetic_fixtures` (independently generated) is copied to `waterflood_app/validation/external_fixtures/` and frozen. Conventions that differ from the M0 suite and had to be handled: rates are surface volumes with B_o = 1.25 / B_w = 1.02 (the loader converts, §6); its `tau_days` are in *time steps* (its forward model uses Δt = 1), so τ is compared after multiplying by the mean month length; its BHP term is −J·Δp·e rather than the Sayarpour (1−e)·Jτ·Δp/Δt — the two differ only by a rescaling of J, which the fit absorbs.
- **M1 · §16 — External `converted_wells` phase-B tolerance not met and not pursued.** The fixture asks for phase-B f_ij within 15 %; with 48 steps, 4 injectors (two of which only inject from the conversion month) and 3 % noise the fit reaches the noise floor (SSE ≈ 2 800 (m³/d)² ≈ 3 % of signal) with f_ij still non-unique (errors up to 100 % on 0.1–0.5 pairs). The fixture's own verifier skips this case. The test asserts well types, the window split at 2020-01, blind R² > 0.8 and τ within 60 %; pair-level recovery there is a known limitation, not a solver bug.
- **M1 · §9 — Aquifer variant recognised, fitted in Milestone 2.** The prompt's M1 acceptance says the tournament "selects the expected variant" on all fixtures, and both aquifer fixtures expect CRMPA, which the build order places in M2. In M1 the tournament recognises the signature (SUM_F_HIGH), marks CRM-Aquifer eligible and recommended (VARIANT_NOT_AVAILABLE, info) and uses the best available model meanwhile; the test asserts exactly that.
- **M1 · §9 — BLIND_FIT_POOR per producer needs both a poor MAPE (> 15 %) and R² < 0.5.** Per-producer blind R² alone is misleading when the held-out window is flat (noise ≈ signal variance — the external README says the same), and it was dragging the badge to LOW on fields with pooled blind R² > 0.93. The badge uses the pooled field blind R².
- **M1 · §6 — Free gas is only assessed when gas PVT (R_s or B_g, or a table) is given.** With the default PVT() any gas column would flag GOR > R_s = 0 on every step.
- **M1 · §5 — Conversion month.** A month with both production and injection (mode B) is the conversion date when the role changes after it; the B step belongs to both role entities (`P-5@P` ends and `P-5@I` starts on that month).
- **M1 · §7 — O_d per sector on the external `sectored_60`.** 96 steps / (15 + 1) = 6.0 fails "O_d > 6" by definition; the warning is correct and reported; the field still fits with blind R² 0.96 per sector.
- **M1 · prompt §2 — Line length raised to 120** (formatting only), and `N803/N806` disabled: J, F, A, S, X are the Atlas symbols.
- **M1 · §19 — `engine.run_engine` is the L1→L3 driver** (well types → grid → clean → pressure → windows → sectors → gates → tournament → oil cut) and is what the API (M3) will wrap. Sector fits run in parallel with joblib processes.

## Milestone 2 — extended models, optimization, workflow (2026-09-03)

- **M2 · §16 — Optimizer truth in the M0 suite re-frozen (generator 1.1.0).** The M0 generator counted the last historical month as the first horizon step (its recursion returns q_last as step 0) and dropped the 24th future month. Corrected: the horizon is the 24 responding months after the last state. Only the `optimizer` block of each `truth.json` changed (streak: gain vs equal split 6.35 % → 6.98 %, vs hold 4.55 % → 5.05 %); the Parquet rate tables and every other truth field are byte-identical, so the immutability test still passes. The engine reproduces the corrected truth to 0.02 %.
- **M2 · §12 — Objective and base definitions.** "Hold current" is the last set-point (`optimize.current_months: 1`); "proportional / equal split" is the same total water spread equally; bounds default to 0 … 2 × mean current rate per injector; forecast liquid continues the fitted recursion from the last historical state; oil uses the fitted WOR–CWI power law with a fitted pre-history offset C₀ (the log-linear fit was exact only with it). Water-cut ceiling and VRR band are off unless the user sets them; a constraint the base already violates is relaxed to the base level and noted, so the optimizer is never infeasible at hold-current.
- **M2 · §12 — Solver.** SLSQP with finite-difference gradients on the posture-aggregated objective, multi-start from hold-current, equal split, a greedy vertex start ordered by marginal value, and Dirichlet draws; a tighter polish from the best point. The greedy start was needed: SLSQP alone stopped 0.3 points short of the bound-constrained optimum. Forecasts are cached per decision vector.
- **M2 · §13 — Robust posture as constraints.** "Never loses oil in any realization" is one inequality per ensemble member (objective(plan) ≥ objective(hold-current)); if the best feasible plan still loses in a member, hold-current is kept and noted. The P10 statistic uses `np.percentile` over members (with a single member it is that member's value).
- **M2 · §9 / Atlas CRM–Aquifer — CRMPA parameterisation.** The Fetkovich tank reduces to one linear ODE in the influx driven by the field imbalance: dẆ_e/dt = −k₁Ẇ_e − k₂(I − Q). Rates identify (Ẇ_e(0), k₁, k₂) and the per-producer allocation a_j (fitted as an extra injector column); J_aq, c_tV_aq and c_tV_r need a pressure scale, taken from static surveys via c_tV_r Δp̄_r = Σ(Ẇ_e + I − Q)Δt; without surveys the pore volumes are reported as not resolvable (§8 "static surveys validate CRMPA pore volume"). The outer loop uses VarPro-only inner fits with a quadratic penalty on injector rows > 1 (so the deficit must go to the aquifer, otherwise Ẇ_e is unidentifiable) and a Nelder–Mead on log parameters. On `aquifer_6x9`: influx 5 331 → 3 097 vs truth 5 600 → 3 287, allocations within 0.01, f_ij within 6 %, blind R² 0.9998; c_tV_r within a factor 1.6 (the survey-scale regression is approximate).
- **M2 · §9 — Static surveys are collected from any well.** The M0 aquifer surveys are tagged to a pseudo-well "FIELD"; pressure prep previously kept static rows only for producers and dropped them. Now any row whose source classifies as static is kept for CRMPA.
- **M2 · §9 — Two-phase and crossflow variants are implemented but only exercised on synthetic unit cases.** No fixture is eligible (all have mean water cut > 0.5; none has ≥ 4 events/well). Two-phase needs a Corey rel-perm curve passed to `run_engine(relperm=…)`; crossflow uses the CRMP allocation as fixed weights and fits c_tV, J, p̄(0) per tank and X on nearest-neighbour edges. The Olenchikov formulation's replacement of allocation weights by productivity coefficients is applied to the inflow side only (injection still enters through weights) — a simplification, recorded here.
- **M2 · Atlas MPI — influence function.** The closed-rectangle line-source series (Valkó et al. 2000) is evaluated with y arguments ordered (y_D ≥ y_wD), which the formula assumes; the prior is the |J_ij| coupling normalised per injector, blended (geometric mean) with the sector's fitted ln f–distance trend and scaled to the median fitted row sum (§11). Unit constants (α₁, k, h, μ, B) cancel in the prior.
- **M2 · §10 — Rolling windows and CUSUM.** 36-month windows, 6-month step, breaks at events; latest window blended with the full fit by blind-R² weights. CUSUM per pair on f_ij(t)/f_ij(t₀) in units of the median multi-start spread (floored at 5 %), k = 0.5, alarm at 2× spread persisting 2 windows; τ per producer likewise. No fixture shows a shift (they are stationary by construction); the detector is tested on a synthetic doubling.
- **M2 · §3 — Workflow policy.** `workflow.separation_policy: log` records `approved_by_originator`; `enforce` blocks. LOW confidence requires an approver override reason. Approval freezes (data hash, config hash, model version, rates, badge) into a digest; edits after approval create a new DRAFT.
- **M2 · §15 — Rules table implemented literally** in `workflow/scheduler.py`; the "parameters shifted" input comes from the rolling re-fit and decides whether a new DRAFT is opened. Quarterly = 90 days since the last full tournament.
- **M2 · §18 — Store.** SQLite (`store.sqlite`) + Parquet snapshots under `snapshots/<data hash>/`; a re-load with identical content is the same snapshot. Postgres is a deployment swap (M5). Code version = `git rev-parse --short HEAD`.
- **M2 · §12 — Economics sign.** On the M0 fixtures (water cut ≈ 99 %) NPV at $70/bbl is negative: water handling and injection costs exceed oil revenue. The objective still ranks plans correctly; the test asserts monotonicity in price rather than a positive NPV.
- **M2 · §9 / §16 — External `aquifer_9x9`: the fixture's expected winner (CRMPA) is not the composite winner.** CRMPA is fitted (influx 3 258 → 3 122 vs truth 3 500 → 2 400; allocations concentrate on P-1/P-2 instead of P-1..P-3) and has the best blind R² (0.869 vs CRMP 0.850), but the composite score ranks CRMP first by ≈ 0.01: AICc (12 extra parameters) and runtime outweigh a +0.02 blind-R² gain. The weights (`tournament.weights`) were not tuned to the fixture; the test asserts the aquifer variant is fitted, ranks in the top 2 and has the best blind R². The M0 aquifer case, whose influx is ≈ 40 % of injection rather than ≈ 25 %, is won by CRMPA outright.

## Milestone 3 — API and users (2026-09-03)

- **M3 · §3.1 — Users.** Local accounts (bcrypt) or SSO pass-through: a trusted identity header (`api.sso_header`, honoured only when `WFO_SSO_TRUST=1`) maps to a registered user; unknown SSO identities are refused (no self-registration). A user may hold several roles; `X-Acting-Role` picks the role for a request (default: the user's most powerful role); admin may act in any role; every action is audited with actor and acting role. Deactivation, never deletion. The first admin is bootstrapped from `WFO_ADMIN_USER` / `WFO_ADMIN_PASSWORD` (or a generated password printed once).
- **M3 · §18 — Secrets.** Connection passwords go to a file secrets store under the store root (`secrets.json`, chmod 600 where the OS allows; `WFO_SECRET_<NAME>` environment variables override) and are referenced by name; the API never returns them. The JWT signing secret is `WFO_JWT_SECRET` or a per-store generated file.
- **M3 · §18 — Query override** is a per-connection SELECT that replaces table reads; reviewer/admin only; the SQL is written to the audit log (truncated to 500 characters).
- **M3 · §19 — Jobs.** A persistent job table plus an in-process thread pool implements the queue interface (submit / status / result); `WFO_JOBS_SYNC=1` runs jobs inline. Celery/RQ is a backend swap behind the same `JobRunner` interface (deployment milestone). Run artefacts (fitted model objects) live in process memory keyed by run id; after a restart the registry still serves results and models, but scenarios need a re-run (HTTP 409 explains this).
- **M3 · §2 — Advanced mode in the API.** `variants` and `threshold_overrides` in a run request are reviewer/admin only (the engineer path never sees them); thresholds are read by reviewer+, changed by admin only, global or per project; the effective config hash changes accordingly and is stored with every run.
- **M3 · §18 — Webhooks.** Admin-managed subscriptions per event (`run.finished`, `recommendation.state_changed`, `recommendation.evaluated`, `alert`); payloads are HMAC-SHA256 signed (`X-WFO-Signature`) when a secret is set; delivery failures are recorded in the audit log and never block the request.
- **M3 · §3 — Evaluations through the API** scale the horizon cumulative-oil ensemble to the evaluation window proportionally (months_after / horizon) as the P10–P90 band; a proper re-forecast over the realised injection is the surveillance milestone's job.
- **M3 · §5 — Snapshots on every load.** Each run (and each wells derivation) saves the mapped source tables as an immutable Parquet snapshot keyed by content hash; identical content is the same snapshot.
- **M3 · §5 — Well filter.** `/wells` accepts field / reservoir / block query parameters resolved against the category table; `/wells/categories` returns the cascading tree.
- **M3 · prompt — Playwright-free API tests** use FastAPI's TestClient with a temporary store and synchronous jobs; they cover every recommendation transition (review, approve, reject from DRAFT and REVIEWED, implement, evaluate at 3 and 6 months), every role refusal on those transitions, the separation policy in both modes, the LOW-confidence override, asset scoping, SSO pass-through, secrets, query override, webhooks and the OpenAPI document.

## Milestone 4 — UI (2026-09-03)

- **M4 · prompt §2 — Node.js.** No Node was installed on the build machine; a portable Node 24 LTS (nodejs.org zip) was unpacked to `C:\code\test\tools\node` and used through `PATH` — no system-wide install, nothing outside the working tree. The Vite dev server is launched from `.claude/launch.json` with that binary.
- **M4 · §6 — Display units are converted at the API edge, not in the browser.** The engine and the store keep SI (m³/d, m³, kPa). The result bundle (`GET /runs/{id}/details`), recommendation responses and the action list are converted to the project's unit system when they are built or served; rates entered in the UI (implemented rates, realised oil) are converted back on the way in. A bundle stored before this change keeps internal units — re-run to refresh.
- **M4 · §4.2 — Plotly bundle size.** `plotly.js-dist-min` (~5 MB minified) is loaded whole; Vite's chunk warning limit is raised rather than code-splitting, because every screen after Run needs Plotly anyway. Fonts come from Google Fonts with system fallbacks (offline deployments must vendor them, M5).
- **M4 · §4.3 — Well map.** Coordinates are drawn with one scale for both axes (no distortion) in the loaded CRS; arrow width ∝ f_ij, opacity ∝ pair confidence = 1 − relative spread of f_ij across the multi-start ensemble; τ can colour the arrows; sector polygons and faults are drawn when supplied (none of the fixtures carries fault geometry); SVG export replaces CSS variables with the token values so the file renders outside the app.
- **M4 · §4.5 — Details is a right drawer**, never a modal; Escape closes it; the Result screen stays visible behind it for side-by-side comparison.
- **M4 · §4.6 — Playwright** uses the installed Edge channel (`channel: msedge`) so no browser download is needed offline; the suite runs against the dev API (`scripts/dev_api.py`, local store, fixed bootstrap admin password) and the Vite dev server, and writes the screen captures committed under `docs/screens/m4_*.png`.
- **M4 · §2 — Advanced overrides** are kept per project in the browser session and sent with the next run request as `variants` / `threshold_overrides`; the API accepts them only for reviewer/admin, records them in the audit log, and the Workflow screen shows them in the approval view.
- **M4 · §4.2 — Tornado.** No economics inputs are exposed on the Result screen yet; the tornado shown in Details is a ±30 % price / ±50 % water-cost sensitivity of the plan's objective value as a placeholder until the NPV objective is wired to the Run screen (M5).

## Milestone 5 — reports, deployment, hardening (2026-09-04)

- **M5 · prompt §2 / §19 — PDF renderer chain.** The prompt fixes WeasyPrint; on the Windows build machine it imports only with the GTK/Pango runtime, which is not installed. `outputs/report.py` renders the same HTML through WeasyPrint when it imports (the Linux images install Pango/Cairo) and otherwise prints it with a headless Chromium/Edge (`--print-to-pdf`, isolated profile directory, file polled until its size is stable because the Windows launcher returns before the child has written it). With neither, the API answers 409 with the plain sentence "no PDF renderer …" and the DOCX/HTML reports remain available. `integration.report_pdf_renderer` (auto | weasyprint | chromium | none) and `WFO_CHROMIUM` pin the choice; `/health/ready` reports which renderer a host has.
- **M5 · §4.2 / §14 — Report figures without matplotlib.** Figures are built as a small scene graph (`outputs/figures.py`: rect, line, polyline, polygon, circle, text) with an SVG back-end for the HTML/PDF report and a Pillow back-end (PNG, 2×) for the DOCX, so both formats show identical figures: well map with f_ij arrows, connectivity matrix, forecast fan, injector efficiency, leaderboard with excluded methods, history-match small multiples with residual strips, Δt/τ step response, outcome range and the economic tornado. The print palette is paper-white with the design tokens' semantic colours (injection blue, production orange, mixed violet, HIGH/MEDIUM/LOW = good/oil/danger).
- **M5 · §14 — Reports are built from stored objects only** (registry row, result bundle, recommendation record, audit): any past run can be reported after a restart, and the report shows exactly what the UI showed (display units applied at the API edge, M4). The watermark (run id · data hash · config hash · code version · generated at/by) is a fixed footer on every page (§18 "exports watermarked with run ID"); the recommendation report adds the workflow history, implemented vs recommended rates, evaluations, the override reason and a red "approved by originator" flag when the separation policy logged it.
- **M5 · §12 / §4.2 — Economic tornado.** `optimize/sensitivity.py` re-evaluates the posture-aggregated ΔNPV (plan − hold-current) on the fitted forecast ensemble under one-at-a-time perturbations (oil price ±30 %, water-handling and injection cost ±50 %, discount rate ±5 points) plus the P10/P90 member range; no re-optimisation. For the cumulative-oil objective only the forecast-range bar exists (economics do not enter). The tornado is stored with the recommendation and drawn in the report and in Details. Economics inputs are now on the Run screen when the NPV objective is chosen.
- **M5 · §12 — NPV unit factor fixed.** `NetPresentValue` evaluated USD/bbl prices against internal m³ rates (`bbl_per_unit` defaulted to 1), so NPV magnitudes were 6.29× too small; rankings were unaffected because revenue and both costs scale together. Now `BBL_PER_M3` is passed. The action list's "expected oil gain" was the objective gain in whatever unit the objective had (currency for NPV); it is now the ensemble-mean cumulative-oil gain regardless of objective, and the marginal-value share falls back to |Δrate| when no marginal value is positive.
- **M5 · §14 — Exports.** XLSX (openpyxl; README sheet with the watermark, one sheet per table, frozen headers, unit suffixes in column names) and a zip of CSVs with the same tables: run, wells, change list, connectivity (f_ij, pair confidence, distance), τ / J per producer, injector efficiency, field and per-well forecast bands, history match (raw / cleaned / model / oil / water / BHP, blind flag), leaderboard, gates, conditions, data quality; recommendation exports add workflow history and recommended vs implemented rates. Model JSON carries f_ij, τ, τ_ij, J, extras and metrics per sector and window plus the registry's internal-unit parameters.
- **M5 · §18 Integration — Writeback.** `POST /recommendations/{id}/writeback` is approver-only (admin acting as approver included), requires state APPROVED / IMPLEMENTED / EVALUATED, a deployment switch (`integration.writeback_enabled`, overridable by the `writeback_enabled` setting) and a connection of the same project flagged `options.wfo_writeback = 1` — read connections hold read-only credentials (§18), so writing needs an explicitly created, write-capable connection. `wfo_*` option keys are app flags and are not passed into the SQLAlchemy URL. One row per injector (target rate in display units, step this week, target date, effective date, recommendation / run / data-hash / config-hash ids, confidence, approver, writer, note) is appended to `wfo_injection_targets` (SQL table created on first write through SQLAlchemy metadata; CSV for file connections). Every writeback is stored in the `writebacks` table, audited and announced by the `writeback.done` webhook.
- **M5 · §18 — Health.** `/health` stays a liveness probe; `/health/ready` checks the store (query + write probe), the snapshot folder, free disk (> 200 MB), the job pool and the PDF renderer, returning 503 when degraded. Compose health checks and the Admin → System tab use it. `code_version` now runs git in the package's own directory and honours `WFO_CODE_VERSION` for images without `.git`.
- **M5 · prompt §2 Packaging — Compose profiles versus the stack table.** The prompt lists api, worker, redis, postgres, ui; the architecture (§18 offline mode, §19 "Postgres (SQLite offline)") makes Postgres and a queue deployment options. The store is SQLite + Parquet on a volume (M2 decision) and jobs run in the API's thread pool behind the `JobRunner` interface (M3 decision). No PostgreSQL or Redis was available on the build machine to verify a swap against, so the profiles ship what was verified: `offline` = one container (API + built UI served by the same process under `/api` and `/`, in-process worker), `prod` = nginx UI + API + nightly backup sidecar on a persistent volume, `dev` = live-reload API + Vite. The Postgres store and an RQ backend remain the documented swap points (`ProjectStore.conn`, `JobRunner`), not silently declared services. Docker itself is not installed on the build machine: the Dockerfiles and compose file were validated for syntax and by review only, and the "working from a clean clone" check must be run on a Docker host — recorded as an open verification in the milestone report.
- **M5 · §4.1 — Fonts vendored.** The three families (latin subsets, woff2, OFL) are served from `ui/public/fonts` with `@font-face` rules; the Google Fonts links are gone, so the UI is offline-capable. Report PNG figures use DejaVu / Arial / Consolas from the host for text.
- **M5 · §18 Retention — Backup.** `scripts/backup.py` copies `store.sqlite` with SQLite's online backup API (consistent while the API runs), adds the immutable snapshot folders and a SHA-256 manifest into a timestamped tar.gz, keeps the newest N (`--retain`), verifies archives and restores them (refusing non-empty targets unless forced). Secrets are excluded unless `--include-secrets`. Snapshots are immutable and content-addressed, so archives are self-contained rather than incremental.
- **M5 · prompt M5 — Load test.** `scripts/load_test.py` builds a 300-well field (10 sealed sectors of 12 injectors + 18 producers, 120 months) in memory with the frozen generator's physics and times the full path with joblib and BLAS pinned to the requested cores. The case is not added to the frozen suite (30 MB of Parquet for a timing case). Result in the milestone report.
- **M5 · §6 — Guides.** `docs/USER_GUIDE.md` (engineer path) and `docs/ADMIN_GUIDE.md` (deployment, users, connections, writeback, health, backups, capacity) complete the deliverables checklist together with `README.md`.
- **M5 · prompt M5 — Where the 300-well time went, and the fix.** The first 300-well run took 666 s (engine 280 s, optimizer 386 s). Profiling one 30-well sector showed the engine's 28 s to be 22 s of CRMIP (8 starts × 18 producers × 26 parameters) and the optimizer's 29 s to be ~6 000 SLSQP objective evaluations that each re-simulated the whole 120-month history plus the plan through the per-producer Python recursion (`predict_field`). `ForecastModel` now caches the recursion state at the last historical step (computed once per model, vectorised over producers / pairs, exact for CRMT / CRMP / CRMIP including the productivity term) and continues only over the plan steps; the other variants keep the full re-simulation. Identical numbers (max difference 1e-13), 30-well sector optimised in 3.6 s instead of 28.7 s. Sector-level process pools were also tried for both phases and measured no faster (engine 306 s vs 280 s) or much slower (optimizer 498 s: cold caches and pickling per worker while the per-producer pool already fills the cores); they stay available behind `solver.sector_parallel: false`.

## Post-M5 review follow-up — outstanding items (2026-09-04)

- **§10 / §15 — Rolling re-fit inside a standard run.** `run_engine` now fits the rolling CRMP windows on the tournament winner (`rolling.mode`: `always` | `auto` | `never`; `auto` skips sectors above `rolling.max_wells_in_run` = 80 wells, which keep the rolling re-fit for the surveillance job), runs the CUSUM detector and emits `CUSUM_SHIFT` conditions into the sector log — the change-alert map in Details and the report conditions table now draw from a real source. `SectorRun` carries `rolling` and `shifts`; the bundle exposes per-window f_ij / τ / blind R² and the blend weights. The forecast ensemble uses the winner members blended with the latest window by blind score (§10), so the optimizer sees the time-varying connectivity. Cost: the streak fixture's run goes from 5 s to 10 s (15 windows); the rolling fit can never fail a run (exceptions leave the full fit in place). Verified on a fixture with a synthetic 60 % strengthening of one pair after month 60: the run raises the alert for that pair and no other.
- **§19 — PostgreSQL store.** The store keeps its SQLite-style code; `store/db.py` is a thin shim that returns the SQLite connection untouched and, for `WFO_DB_URL=postgresql://…`, wraps psycopg with the four translations the code needs (`?` → `%s`, `INSERT OR REPLACE` → `ON CONFLICT (pk) DO UPDATE`, `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING`, `RETURNING` for the two serial keys, `AUTOINCREMENT` → `BIGSERIAL` in the DDL). Primary keys and columns are parsed from the same DDL string, so the schema stays single-sourced. Parquet snapshots and run artefacts stay on the shared store folder; only metadata moves to PostgreSQL. Connections are reused per thread and committed on context exit, the contract the callers already relied on. Verified against a real PostgreSQL 16 (portable binaries on the build machine, a postgres service in CI): store, registry, audit sequence, users, jobs and the full API flow (`tests/test_store_postgres.py`). Backups use `pg_dump --format=custom` next to the Parquet files and `pg_restore` on restore.
- **§19 — Worker process without a broker.** Rather than Redis + RQ, the persistent `jobs` table is the queue: `WFO_JOBS_MODE=external` makes the API only insert rows, and `python -m waterflood_app.api.worker` claims the oldest queued job with an atomic conditional UPDATE and runs it with the same service code. Several workers can share one PostgreSQL store; with SQLite keep one worker per file. Run artefacts (fitted models, ensemble, plan) are now persisted with joblib under `store/artifacts/<run id>.joblib` and reloaded on demand, so scenarios and recommendation creation work from any API process and after restarts — this also retires the M3 "run results are not in memory (service restarted)" 409. The `prod` profile runs `postgres`, `api` (external mode), `worker` (scalable) and the backup sidecar.
- **Verified on GitHub Actions (`Saipem125/CRM-NEW`, commit `2e8b0d1`).** No Docker on the build PC, so the repository was pushed and CI became the second machine: the `docker-build` job builds the api / offline / ui images and validates all three compose profiles; the Python jobs run the full suite on 3.11 and 3.12 against a PostgreSQL service. Two CI-only findings were fixed on the way: the mypy target was pinned to 3.11 (numpy's stubs use the 3.12 `type` statement) and the 10-minute fixture bound, specified for 8 cores, is now scaled by core count (the runner has 2). Starting a stack with `docker compose up` on a Docker host remains the last unexecuted step.
